# NCA BATCH 4 PRIVATE CTF PLATFORM

## Anti-Cheat & Competition Integrity System

**Document:** ctf7.txt
**Version:** 1.0
**Status:** System Specification
**Project:** NCA Batch 4 Private CTF Platform
**Purpose:** Define a fair, evidence-based system for detecting, investigating, and handling cheating, flag sharing, collusion, and suspicious competition activity.

---

# 1. Purpose

The NCA Batch 4 CTF must provide an integrity system that helps administrators identify suspicious activity without incorrectly punishing legitimate participants.

The system should detect and record:

* Flag sharing
* Account sharing
* Excessive suspicious submissions
* Coordinated solves
* Suspiciously synchronized activity
* Duplicate solution patterns
* Multiple accounts controlled by one participant
* Unauthorized access to challenge infrastructure
* Attempts to manipulate scoring
* Submission abuse
* Post-solve collaboration patterns
* Suspicious administrative activity

The system must provide **evidence and risk indicators**, not blindly ban participants.

---

# 2. Core Principle

The system must follow:

```text
Detection
    ↓
Evidence
    ↓
Risk Score
    ↓
Admin Review
    ↓
Decision
    ↓
Action
    ↓
Audit Log
```

Never:

```text
Suspicious signal
      ↓
Automatic permanent ban
```

A single indicator should normally not be enough for disqualification.

---

# 3. Why IP Address Alone Is Not Enough

Many students may use:

```text
Same Wi-Fi
Same college network
Same ISP
Same NAT gateway
Mobile hotspot
VPN
```

Therefore:

```text
Same IP ≠ Same Person
```

The system must never automatically disqualify a team solely because two teams have the same public IP.

IP should be treated as one signal among many.

```text

Normal

Low concern
```

# 12. Flag Sharing Detection

One of the primary requirements is detecting when a participant shares a flag.

Example:

```text
Team A solves Challenge X
       ↓
Team B submits identical flag
       ↓
Team B solves shortly afterward
```

The system should identify the relationship.

---

# 13. Flag Submission Fingerprinting

When a flag is submitted, store a secure fingerprint rather than unnecessarily exposing the actual flag.

Example:

```text
flag_hash
```

This allows the system to identify identical submissions without storing plaintext submission data unnecessarily.

---

# 14. Shared Flag Indicator

Example:

```text
Team A:
Accepted flag
10:30:15

Team B:
Same flag
10:30:21
```

This generates:

```text
ALERT:
POSSIBLE_FLAG_SHARING
```

The alert should contain:

```text
Challenge
Team A
Team B
Submission timestamps
Time difference
Flag fingerprint
```

---

# 15. Important Exception

Identical flags are expected when a challenge has a static flag.

Therefore:

```text
Same flag ≠ cheating
```

The system must distinguish:

```text
Static challenge flag
```

from:

```text
Team-specific/dynamic flag
```

Flag-sharing detection is significantly stronger for dynamic/team-specific flags.

---

# 16. Dynamic Flag Support

Future challenges can use:

```text
NCA{team_specific_secret}
```

Example:

```text
Team A:
NCA{8a91...}

Team B:
NCA{f82c...}
```

If Team B submits Team A's flag:

```text
Team A's flag
       ↓
Team B submission
       ↓
DIRECT FLAG SHARING INDICATOR
```

This provides strong evidence.

---

# 17. Flag Exposure Tracking

For dynamic challenges, the platform should know which flag belongs to which team.

Example:

```text
challenge_id
team_id
flag_identifier
issued_at
```

The actual flag should be protected.

---

# 18. Submission Timeline Analysis

The system should analyze solve timing.

Example:

```text
Team A solves
12:01:00

Team B solves
12:01:05

Team C solves
12:01:07
```

If this repeatedly happens across unrelated challenges, it may indicate coordination.

One synchronized solve should not automatically trigger punishment.

Repeated patterns should increase risk.

---

# 19. Suspicious Solve Chains

Example:

```text
Challenge 1
Team A → solve
Team B → 4 seconds later

Challenge 2
Team A → solve
Team B → 7 seconds later

Challenge 3
Team A → solve
Team B → 6 seconds later
```

The system can identify:

```text
Repeated solve-following relationship
```

and create an alert.

---

# 20. Account Relationship Detection

The platform should detect suspicious account relationships using non-invasive signals.

Possible signals:

```text
Repeated same IP
Repeated same session/device fingerprint
Highly synchronized login activity
Shared infrastructure patterns
Unusual account creation patterns
Repeated simultaneous behavior
```

These are indicators, not proof.

---

# 21. IP Address Handling

IP addresses should be handled carefully.

Prefer storing:

```text
HMAC/IP hash
```

for long-term correlation where the plaintext IP is not required.

Example:

```text
HMAC-SHA256(IP + server_secret)
```

This allows:

```text
same IP?
```

to be detected without unnecessarily exposing the address in ordinary admin views.

---

# 22. Admin IP Access

Authorized administrators may need the original IP for investigations.

If retained, access should be restricted.

The system should record:

```text
Who viewed sensitive investigation information
When
Why
```

---

# 23. User-Agent Correlation

A normalized user-agent fingerprint may be stored.

Example:

```text
browser
OS family
browser family
```

Avoid treating a browser fingerprint as a unique identity.

It is only another correlation signal.

---

# 24. Device Fingerprinting

The V1 system should avoid invasive device fingerprinting.

Do NOT attempt to collect:

```text
hardware serial numbers
MAC addresses over the Internet
private filesystem information
```

A simple session/browser signal is sufficient for V1.

---

# 25. VPN / Proxy Detection

VPN use should not automatically be treated as cheating.

The system may flag:

```text
Known VPN/proxy
Rapid IP changes
Impossible geographic transitions
```

but these should only contribute to risk.

---

# 26. Multiple Account Detection

Potential signal:

```text
Account A
      │
      ├── same IP
      ├── same session characteristics
      └── highly synchronized activity
      │
Account B
```

The system creates:

```text
POSSIBLE_MULTI_ACCOUNT
```

The administrator investigates.

---

# 27. Team Membership Restrictions

The platform should define competition rules such as:

```text
Maximum team size
One account per participant
One team per participant
```

The backend should enforce these rules.

---

# 28. Account Sharing

Account sharing may be detected when:

```text
Account A
   │
   ├── Session from Location/Network A
   ├── sudden activity pattern change
   └── Session from Network B
```

A sudden change alone should not result in punishment.

Examples of legitimate reasons:

```text
Mobile network
VPN
College network
Home network
```

---

# 29. Concurrent Sessions

The system should record concurrent sessions.

Example:

```text
Account A

Session 1 → 10:00
Session 2 → 10:01
Session 3 → 10:02
```

Multiple simultaneous sessions may generate:

```text
CONCURRENT_SESSION
```

The platform may optionally limit active sessions according to competition rules.

---

# 30. Submission Abuse

Detect:

```text
Very high submission frequency
Automated submission attempts
Large numbers of invalid flags
Repeated identical submissions
```

Example:

```text
500 submissions
in 30 seconds
```

should trigger:

```text
SUBMISSION_ABUSE
```

---

# 31. Rate Limiting

The flag submission API must have rate limiting.

Example conceptual rule:

```text
Maximum submissions:
X per minute per user/team
```

The exact value should be configurable.

Rate limits should not make normal CTF gameplay frustrating.

---

# 32. Brute-Force Submission Detection

Example:

```text
Team A
100 incorrect flags
within 1 minute
```

Generate:

```text
BRUTE_FORCE_SUBMISSION
```

Possible action:

```text
Temporary submission cooldown
```

rather than immediate disqualification.

---

# 33. Automated Tools

The system should not assume:

```text
Burp Suite
ffuf
pwntools
sqlmap
```

means cheating.

These are legitimate CTF tools.

Detection must focus on:

```text
Competition rule violations
```

rather than normal security tooling.

---

# 34. Challenge Access vs Solve

Track:

```text
Challenge viewed
Challenge downloaded
Challenge instance started
Challenge solved
```

This allows better timeline reconstruction.

Example:

```text
10:00 Challenge viewed
10:05 Challenge downloaded
10:30 Flag submitted
10:31 Accepted
```

---

# 35. Suspicious Download Patterns

Example:

```text
Team A downloads challenge file
Team B immediately downloads same file
Team B solves 5 seconds later
```

This may be an indicator.

However, downloadable challenges are normally shared resources, so the signal should have low weight.

---

# 36. Behavioral Correlation

The integrity engine can compare teams across multiple challenges.

Example:

```text
Team A solves first
Team B follows

Repeated 8 times
```

This is stronger than:

```text
Team B follows once
```

The system should detect repeated relationships.



---

# 57. Anti-Cheat Transparency

The public competition rules should explain broadly:

```text
Flag sharing
Account sharing
Unauthorized collaboration
Automated abuse
Score manipulation
Infrastructure attacks outside challenge scope
```

The platform does not need to reveal every detection mechanism.

---

# 58. Don't Reveal Detection Algorithms

Participants should not be shown:

```text
Exact risk score formula
Exact alert thresholds
Exact correlation weights
Internal fingerprints
Admin detection rules
```

Otherwise participants may attempt to evade detection.

---

# 59. Integrity Rules

The competition rules should clearly state:

```text
Do not share flags.
Do not share solutions during the competition.
Do not use another participant's account.
Do not attack the CTF infrastructure itself.
Do not intentionally disrupt other teams.
Do not manipulate scoring.
Only attack systems explicitly included in challenges.
```

---

# 60. Out-of-Scope Attacks

Participants must not attack:

```text
CTF database
Admin panel
Docker host
Infrastructure manager
Other teams' challenge instances
Authentication backend
DNS infrastructure
```

unless explicitly included as a challenge.

This is especially important because the platform itself is a cybersecurity target.

Participants should understand:

```text

      ↓

      ↓

```

NOT:

```text
CTF backend
CTF database
Docker host
Admin API
```

# 62. Integrity Event Retention

The platform should retain relevant events for the duration of the competition and an appropriate period afterward.

Suggested:

```text
Competition period
      +
Investigation period
```

Retention duration should be configurable.

# 63. Privacy

Collect only information necessary for:

```text
Authentication
Competition integrity
Security
Administration
```

Avoid unnecessary surveillance.

Do not collect:

```text
Microphone
Camera
Keystrokes
Personal files
Browser history
```

The anti-cheat system does not need these.

---

# 64. No Keylogging

The platform must never implement:

```text
Keylogger
Screen recording
Clipboard monitoring
```

for ordinary participants.

These are unnecessary for a legitimate CTF integrity system.

---

# 65. No Invasive Tracking

Avoid invasive fingerprinting.

The system should rely primarily on:

```text
Submission events
Authentication events
Challenge events
Server-side logs
Flag relationships
Timing relationships
Rate limits
Account/team relationships
```

# 69. Example Risk Calculation

Conceptually:

```text
Risk Score =
Flag Sharing
+
Submission Abuse
+
Account Correlation
+
Repeated Timing
+
Other Indicators
```

Example:

```text
Dynamic flag mismatch       +80
Repeated solve correlation  +10
Same network                +3
High submissions             +7

Total                        100
```

However, exact weights must be tuned during testing.

---

# 70. Avoid Double Counting

The engine must avoid counting the same event multiple times.

Example:

```text
Same dynamic flag
```

should not create:

```text
+80
+80
+80
```

because three detection rules happened to observe it.

A single underlying event should have controlled scoring.

---

# 71. Confidence vs Risk

Separate:

```text
Risk
```

from:

```text
Confidence
```

Example:

```text
High risk + low confidence
```

means:

```text
Investigate carefully
```

not:

```text
Immediately ban
```

# 87. V1 Anti-Cheat Scope

Do NOT attempt to build an AI-based cheating detector initially.

V1 should use deterministic server-side rules.

Implement:

```text
Flag relationship detection
Submission rate detection
Repeated timing detection
Session correlation
Account/team relationship detection
Audit logs
Admin alerts
Risk levels
Investigation workflow
Disqualification
```

This is sufficient for the first competition.

# 89. What the System Should NOT Do

Never automatically disqualify because of:

```text
Same IP
Same Wi-Fi
Same ISP
VPN usage
Same browser
Similar solve time once
Same public challenge flag
Using common CTF tools
```

These are weak signals.

---

# 90. Strong Evidence

Strong evidence includes:

```text
Submitting another team's unique dynamic flag
Direct evidence of account sharing
Repeated coordinated activity with multiple indicators
Manipulating the CTF backend
Unauthorized access to protected infrastructure
Explicitly sharing flags/solutions where verified
```

# 92. Final Security Principle

The NCA Batch 4 anti-cheat system is not designed to "spy" on participants.

It is designed to provide administrators with enough server-side evidence to determine whether competition rules were violated.

The system should prioritize:

```text
Fairness
Evidence
Privacy
Transparency
Auditability
Human review
```

over aggressive automated punishment.

# 93. Final V1 Acceptance Criteria

The Anti-Cheat system is complete when:

```text
[ ] All important events are logged
[ ] Flag submissions are fingerprinted
[ ] Dynamic flags can be associated with teams
[ ] Wrong-team dynamic flags are detected
[ ] Submission rate abuse is detected
[ ] Suspicious timing patterns can be detected
[ ] Account/session anomalies are logged
[ ] Risk levels are calculated
[ ] Admin alerts are generated
[ ] Admin can investigate an alert
[ ] Admin can view timelines
[ ] Admin can add investigation notes
[ ] Admin can dismiss alerts
[ ] Admin can issue warnings
[ ] Admin can freeze teams
[ ] Admin can disqualify teams
[ ] All disciplinary actions are audited
[ ] Participants cannot access integrity data
[ ] IP data is handled securely
[ ] Same-IP situations do not automatically cause punishment
[ ] Appeals can be supported
```

# 95. Final Principle for MonkeyCode Implementation

The anti-cheat system must be implemented as a **modular subsystem**, not scattered throughout the application.

Recommended backend structure:

```text
backend/
├── modules/
│   ├── auth/
│   ├── users/
│   ├── teams/
│   ├── challenges/
│   ├── submissions/
│   ├── leaderboard/
│   │
│   └── integrity/
│       ├── events/
│       ├── rules/
│       ├── scoring/
│       ├── alerts/
│       ├── investigations/
│       ├── actions/
│       └── audit/
```

The integrity module should be independently extensible.

Future detection rules should be addable without rewriting the CTF platform.
