# NCA BATCH 4 PRIVATE CTF PLATFORM

## API & Backend Architecture Specification

**Document:** ctf5.txt
**Version:** 1.0
**Status:** Backend/API Specification
**Project:** NCA Batch 4 Private CTF Platform
**Purpose:** Define the backend architecture, API contracts, authentication, authorization, scoring, validation, rate limiting, error handling, and administrative operations.

---

# 1. Purpose

This document defines how the frontend, backend, database, challenge infrastructure, and administrative systems communicate.

The backend must provide secure APIs for:

* Authentication
* User management
* Team management
* Challenge browsing
* Challenge details
* Challenge files
* Hint management
* Flag submission
* Scoring
* Leaderboards
* Announcements
* Profiles
* Docker challenge infrastructure
* Integrity/anti-cheat monitoring
* Administrative operations
* Audit logging
* Competition configuration

The API is the authoritative interface between the frontend and backend.

The frontend must never directly access the database.

---

# 2. Recommended Backend Architecture

The backend should follow a layered architecture.

```text
Frontend
   │
   ▼
API Routes / Controllers
   │
   ▼
Middleware
   │
   ├── Authentication
   ├── Authorization
   ├── Rate Limiting
   ├── Validation
   └── Security
   │
   ▼
Services
   │
   ├── Auth Service
   ├── Challenge Service
   ├── Submission Service
   ├── Scoring Service
   ├── Team Service
   ├── Integrity Service
   └── Admin Service
   │
   ▼
Repositories / Database Layer
   │
   ▼
MySQL / MariaDB
```

Challenge infrastructure is separate:

```text
Backend
   │
   ▼
Challenge Infrastructure Manager
   │
   ▼
Docker
   │
   ├── Web Challenge
   ├── TCP/Pwn Challenge
   └── Other Challenge Services
```

The participant-facing API must never directly expose Docker control.

# 4. API Response Format

Use a consistent JSON response structure.

## Success

```json
{
  "success": true,
  "data": {},
  "message": "Operation successful"
}
```

## Error

```json
{
  "success": false,
  "error": {
    "code": "INVALID_REQUEST",
    "message": "The request could not be processed"
  }
}
```

Do not expose:

* SQL errors
* Stack traces
* Database credentials
* Internal filesystem paths
* Docker secrets
* Flag hashes
* Internal security information

in normal production responses.

# 6. Authentication Architecture

The platform must use secure server-side authentication.

Recommended approach:

```text
Login
  ↓
Validate credentials
  ↓
Create authenticated session
  ↓
Secure session cookie
  ↓
Authenticated API requests
```

For a web-first platform, prefer secure HTTP-only cookies over storing authentication tokens in `localStorage`.

Cookie requirements:

```text
HttpOnly
Secure
SameSite=Lax or Strict
```

Production must use HTTPS.

# 10. Login Security

Implement:

* Rate limiting
* Generic invalid-credential responses
* Secure password hashing
* Session regeneration after login
* Session invalidation after logout
* Account status checking
* Optional account lockout/risk controls

Do not reveal whether the username or password was incorrect.

Prefer:

```text
Invalid username or password.
```

instead of:

```text
Username exists but password is wrong.
```


```text

```


---

# 28. Flag Submission Processing

The backend must:

```text
1. Authenticate
2. Determine current user
3. Determine current team
4. Check competition status
5. Check challenge status
6. Rate-limit submission
7. Normalize flag
8. Hash submitted flag
9. Compare against active flag
10. Record submission
11. Check whether team already solved
12. Determine First Blood
13. Calculate points
14. Create solve
15. Update cached score
16. Create audit event
17. Trigger integrity analysis
18. Commit transaction
```

---

# 32. Already Solved

If the team has already solved the challenge:

```json
{
  "success": true,
  "data": {
    "correct": true,
    "already_solved": true
  },
  "message": "Your team has already solved this challenge."
}
```

The system must not award points again.

---

# 33. Submission Rate Limiting

Flag submission must have strict rate limiting.

Example initial policy:

```text
Maximum:
10 submissions / minute / user

Maximum:
20 submissions / minute / team
```

These values must be configurable.

A `429 Too Many Requests` response should be returned when exceeded.

---

# 34. Rate Limiting Architecture

Rate limits should consider:

```text
User
Team
IP
Endpoint
```

Do not rely only on IP because participants may share networks.

Do not rely only on username because accounts can be abused.

# 55. CSRF Protection

If authentication uses cookie-based sessions, state-changing requests must have CSRF protection.

Protect:

```text
POST
PUT
PATCH
DELETE
```

especially:

```text
POST /submit
POST /teams
POST /admin/...
```

GET requests must not perform state-changing operations.

---

# 56. Input Validation

All API inputs must be validated server-side.

Validate:

```text
Type
Length
Format
Range
Allowed values
Relationships
Authorization
```

Examples:

```text
points > 0

difficulty ∈
easy, medium, hard, insane
```

Never rely only on HTML input validation.

---

# 57. SQL Injection Protection

All database queries must use prepared statements / parameterized queries.

Never construct:

```text
SELECT * FROM users WHERE username = '$username'
```

from raw user input.

Use parameterized queries through the application's database abstraction layer.

---

# 58. Mass Assignment Protection

Do not automatically map request JSON to database records.

Bad:

```text
User::update(request.body)
```

A participant could submit:

```json
{
  "role": "super_admin",
  "score": 999999
}
```

Instead explicitly select allowed fields.

# 60. Error Handling

Never expose internal exceptions.

Bad:

```text
SQLSTATE[23000]: Integrity constraint violation...
```

Production response:

```json
{
  "success": false,
  "error": {
    "code": "CONFLICT",
    "message": "The requested operation could not be completed."
  }
}
```

Detailed errors may be logged internally.



```text

```

# 72. Integrity Detection Principle

The system should operate on **signals**, not assumptions.

Example:

```text
Team A solves at 14:30
Team B solves at 14:30:03
```

This alone does not prove cheating.

Possible evidence:

```text
Timing correlation
Repeated suspicious patterns
Submission behavior
Shared infrastructure indicators
Flag similarity where appropriate
Account relationships
```

The system generates:

```text
Risk Score
```

rather than automatically issuing punishment.

---

# 73. Automated Actions

The integrity engine may automatically:

```text
Create alert
Increase risk score
Notify administrators
Temporarily flag an event
```

It should NOT automatically:

```text
Permanently ban a team
Delete solves
Delete accounts
Change scores
```

without explicit competition policy and administrative authorization.

# 80. Implementation Rule for AI Coding Agents

MonkeyCode must treat this document and the previous architecture documents as specifications.

It must not:

* Invent alternate authentication architecture without approval
* Change scoring logic without approval
* Expose challenge flags
* Trust client-supplied scores
* Trust client-supplied team IDs
* Give participants Docker access
* Bypass RBAC
* Remove audit logging
* Automatically disqualify teams
* Hardcode competition settings
* Store plaintext passwords
* Store production secrets in source code
* Modify unrelated components while implementing an API feature

When a requirement is ambiguous, the implementation should prefer the safest architecture and identify the ambiguity before making a major architectural change.
