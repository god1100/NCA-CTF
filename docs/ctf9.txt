# 2. Backend Architecture

Use a layered PHP architecture.

```text
Routes
   ↓
Middleware
   ↓
Controllers
   ↓
Services
   ↓
Repositories
   ↓
Database
```

Recommended structure:

```text
app/
├── Controllers/
├── Models/
├── Services/
├── Repositories/
├── Middleware/
└── Infrastructure/
```

Do NOT introduce Laravel or another full framework unless explicitly approved later.

Use:

```text
PHP 8.x
PDO
MySQL/MariaDB
```

---

# 3. Frontend Architecture

Vanilla JavaScript

Shared CSS

# 5. Authentication & Authorization

Use four permission concepts:

```text
Global roles:
- participant
- challenge_admin
- super_admin
```

Team-level role:

```text
team_captain
```

A participant can be a team captain without becoming a global administrator.

Authorization must therefore consider:

```text
User Global Role
+
Team Membership
+
Team Captain Status
```

Never trust client-provided:

```text
role
team_id
user_id
permissions
score
```

---

# 6. Authentication Security

Use:

```text
PHP password_hash()
Argon2id when available
bcrypt fallback
```

Sessions must use:

```text
HttpOnly
Secure
SameSite
```

Session IDs must be regenerated after successful login.

Implement:

```text
Registration
Login
Logout
Change password
Session expiration
Authorization middleware
```

Password reset email infrastructure is NOT required for V1.

Password reset can be added later.

```text

```

with an appropriate action type/status.

---

# 9. Integrity Philosophy

The integrity system is:

```text
Detection
   ↓
Evidence
   ↓
Risk Score
   ↓
Admin Review
   ↓
Decision
   ↓
Audit
```

A single suspicious signal must never automatically disqualify a participant.

The system must provide evidence and allow administrators to make the final decision.

---

# 10. Anti-Cheat Boundaries

The system may use reasonable CTF-related signals such as:

```text
Flag submission timing
Submission history
Flag fingerprints
Team relationships
Account relationships
Shared flags
Suspicious solve patterns
IP correlation where appropriate
Session correlation
```

The system must NOT implement:

```text
Keylogging
Device fingerprinting
Screen monitoring
Invasive surveillance
Reading private files
Monitoring unrelated applications
```

Only competition-relevant data should be collected.

# 17. Challenge Files

Challenge files must:

```text
Have configurable size limits
Be validated
Be stored outside executable web paths
Not permit arbitrary server-side execution
Be accessible only through authorized challenge endpoints
```

Default maximum:

```text
100 MB per challenge file
```

This value should be configurable.

# 18. Hints

Hints are included in V1.

Hints are optional per challenge.

Each hint may have:

```text
Content
Point penalty
Reveal status
```

Example:

```text
Hint 1: -10 points
Hint 2: -25 points
```

---

# 19. Scoring

V1 uses static scoring.

```text
Final Score =
Base Challenge Points
+ First Blood Bonus
- Hint Penalty
```

Scoring is calculated server-side.

Clients must never submit or determine their own score.

Dynamic difficulty/scoring is deferred to a future version.

---

# 20. Flag Architecture

V1 must support:

```text
Static flags
```

Flags must never be stored in plaintext where avoidable.

Store:

```text
flag_hash
```

and verify submissions using secure comparison.

The architecture must remain compatible with dynamic per-team flags.

Dynamic flags are a planned extension, not a requirement for the first working platform.

---

# 21. Flag Submission

Submission flow:

```text
Authenticate
    ↓
Validate competition state
    ↓
Validate challenge
    ↓
Validate team membership
    ↓
Rate limit
    ↓
Validate flag
    ↓
Transaction
    ↓
Create submission
    ↓
Create solve if correct
    ↓
Calculate score
    ↓
Check first blood
    ↓
Update leaderboard
    ↓
Create audit/integrity event where appropriate
```

Duplicate solves must be prevented by database constraints.

---

# 22. Leaderboard

Primary ordering:

```text
Total score DESC
```

Tie-break:

```text
Earliest timestamp at which the team reached that score
```

The authoritative source is the `solves` table.

A cached team score may be maintained for performance, but it must never become the only source of truth.

---

# 23. Docker Infrastructure

Docker is isolated from the platform.

Never expose the Docker socket directly to the participant-facing application.

Use an Infrastructure Manager abstraction.

```text
CTF Backend
     ↓
Infrastructure Manager
     ↓
Docker
```

---

# 24. Docker V1 Scope

V1 should initially support:

```text
Shared challenge containers
```

where safe and appropriate.

Do NOT make per-team containers mandatory for every challenge in the first Docker implementation.

The first objective is to establish:

```text
Build
Start
Stop
Reset
Health check
Resource limits
Port allocation
```

for challenge containers.

---

# 25. Dynamic / Per-Team Containers

Per-team containers are a planned extension.

They should be introduced after the shared-container infrastructure is stable.

Use them when a challenge requires:

```text
Isolation
Unique state
Dynamic flags
Team-specific environment
```

The database/API design must not prevent this future extension.

---

# 26. Challenge Instance Isolation

Challenge containers must not automatically access:

```text
CTF database
Host filesystem
Docker socket
Admin API
Other teams' containers
```

unless a specific challenge intentionally requires such access.

Network separation must be enforced.

---

# 27. Session Storage

V1:

```text
Native PHP sessions
```

Use secure cookies.

Redis is optional and deferred.

Do not add Redis merely because it may be useful later.

---

# 28. Rate Limiting

Rate limiting is required in V1.

Initial implementation may use a database-backed or application-level mechanism.

The architecture should allow future migration to Redis.

Rate limits should be independently considered for:

```text
User
Team
IP
Endpoint
```

Do not rely solely on IP-based limits.
