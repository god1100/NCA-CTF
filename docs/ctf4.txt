# NCA BATCH 4 PRIVATE CTF PLATFORM

## Database Architecture, ERD & SQL Specification

**Document:** ctf4.txt
**Version:** 1.0
**Status:** Architecture Specification
**Project:** NCA Batch 4 Private CTF Platform
**Database:** MySQL / MariaDB
**Purpose:** Define the complete relational database architecture before application implementation.

---

# 1. Purpose

This document defines the database architecture for the NCA Batch 4 Private CTF Platform.

The database must support:

* User authentication
* Role-based access control
* Batch management
* Team management
* Challenge management
* Challenge categories
* Challenge files
* Challenge hints
* Secure flag validation
* Flag submissions
* Challenge solves
* Scoring
* First Blood
* Leaderboards
* Announcements
* Docker challenge instances
* Integrity/anti-cheat events
* Integrity evidence
* Audit logging
* Warnings
* Team/user disqualification
* Competition settings

The database must be designed for security, consistency, maintainability and future expansion.

---

# 2. Database Technology

Use:

* MySQL 8.x or MariaDB equivalent
* InnoDB storage engine
* UTF-8 / utf8mb4 character set
* UTC timestamps internally
* Foreign key constraints
* Appropriate indexes
* Transactions for scoring and submissions

The application must access the database through prepared statements.

---

# 3. Core Design Principles

## 3.1 Do not store plaintext passwords

Passwords must be stored using a secure password hashing algorithm such as Argon2id or bcrypt.

Example:

```text
password_hash
```

Never:

```text
password
```

---

## 3.2 Do not expose challenge flags

Participant-accessible application code must never return the plaintext challenge flag.

Prefer storing:

```text
flag_hash
```

rather than exposing:

```text
NCA{secret_flag}
```

The flag validation process should hash the submitted value and compare it with the stored secure representation.

---

## 3.3 Never trust client-side scores

The browser must never be allowed to submit:

```text
score = 500
```

The server calculates all points.

The authoritative score comes from server-side challenge and solve records.

---

## 3.4 Preserve historical records

Do not physically delete important competition records.

Prefer status fields such as:

```text
active
suspended
archived
disqualified
```

This is particularly important for:

* Users
* Teams
* Challenges
* Submissions
* Solves
* Integrity investigations
* Audit logs

---

## 3.5 Use transactions for critical operations

A successful flag submission and score update must happen inside a database transaction.

Conceptually:

```text
BEGIN TRANSACTION

Validate submission
Check previous solve
Create submission
Create solve
Calculate score
Update score
Check First Blood
Create audit event

COMMIT
```

If anything fails:

```text
ROLLBACK
```

This prevents partial scoring.

# 18. SCORE CALCULATION

The score should be calculated server-side.

Basic formula:

```text

base_points
+ first_blood_bonus
- hint_penalty
```

```text

200

First Blood:
25

-25

200
```

# 29. Referential Integrity

Use foreign keys wherever relationships exist.

For example:

```text
submissions.challenge_id
REFERENCES challenges.id
```

Do not allow orphan records.

However, cascading deletes should be used carefully.

For competition records, prefer preserving historical data.

Example:

```text
User suspended
```

rather than deleting the user.

---

# 30. Soft Deletion

For important entities, use status/archive fields instead of physical deletion.

Recommended for:

```text
users
teams
challenges
announcements
```

Example:

```text
challenges.status = archived
```

instead of:

```text
DELETE FROM challenges
```

Historical submissions and solves must remain valid.

---

# 31. Competition Score Architecture

The score displayed on the leaderboard should be derived from successful solves.

Conceptually:

```text
TEAM
 │
 └── SOLVES
       │
       ├── base_points
       ├── first_blood_bonus
       ├── hint_penalty
       └── points_awarded
                │
                ▼
           TEAM SCORE
```

The `teams.score` field may be maintained as a cached value.

If there is ever a discrepancy:

```text
solves
```

remain the authoritative scoring history.

---

# 32. Leaderboard Query Concept

The leaderboard should primarily be based on:

```text
SUM(solves.points_awarded)
```

grouped by:

```text
team_id
```

Then sorted by:

```text
score DESC
```

Tie-breaking can later be defined using:

```text
total_score DESC
last_solve_time ASC
```

This means the team that reached the score earlier wins the tie.

# 33. Submission Processing Transaction

A correct submission should follow this logical process:

```text
1. Authenticate user

2. Verify user is eligible

3. Verify competition is LIVE

4. Verify team membership

5. Verify challenge is PUBLISHED

6. Apply submission rate limit

7. Normalize submitted flag

8. Hash submitted flag

9. Compare against active flag hash

10. Record submission

11. If incorrect:
       COMMIT submission
       return incorrect

12. If correct:
       Check whether team already solved

13. If already solved:
       record duplicate
       COMMIT
       return already solved

14. Determine First Blood

15. Calculate score

16. Create solve

17. Update team score

18. Create audit event

19. Generate integrity-analysis event

20. COMMIT
```

---

# 34. Race Condition Protection

Two members of the same team may submit the correct flag at almost exactly the same time.

The database must prevent:

```text
Team A solves Challenge X
Team A solves Challenge X
```

twice.

Use:

```text
UNIQUE(team_id, challenge_id)
```

on `solves`.

The application must also use transactions/locking where required.

---

# 35. Flag Security

The database must never expose flags through:

* Participant API
* Participant page
* Challenge JSON
* Browser source
* Public JavaScript
* Downloadable frontend assets

Administrators may access flag management through protected backend operations.

---

# 36. IP Address Handling

IP addresses may be stored for:

* Security
* Rate limiting
* Integrity analysis
* Audit logs

However:

```text
Same IP ≠ automatic cheating
```

Many participants may share the same public network.

IP correlation must only be one signal in the integrity system.

---

# 37. Session Identifier Handling

Submission records may contain a server-side session reference.

Do not store raw authentication secrets as evidence.

Use an internal identifier or safe fingerprint/reference.

Never expose session identifiers to participants or administrators unnecessarily.

---

# 38. Audit Log Security

Audit logs must be append-oriented.

Normal administrators should not be allowed to modify historical audit records.

Only authorized system-level operations should be capable of archival/maintenance.

---

# 39. Database User Permissions

Production should use a dedicated database user.

Do not use:

```text
root
```

from the application.

Recommended conceptual permissions:

```text
Application DB User
├── SELECT
├── INSERT
├── UPDATE
└── DELETE where required
```

Administrative database operations should use a separate privileged account.

# 46. SQL Schema Implementation Requirements

When implementing the schema:

* Use InnoDB
* Use utf8mb4
* Use foreign keys
* Use indexes
* Use unique constraints
* Use NOT NULL wherever appropriate
* Use sensible defaults
* Avoid unnecessary ENUM usage where future extensibility is important
* Use transactions for scoring
* Do not create unnecessary duplicate fields
