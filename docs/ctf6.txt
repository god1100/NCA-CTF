# NCA BATCH 4 PRIVATE CTF PLATFORM

## Docker & Challenge Infrastructure Specification

**Document:** ctf6.txt
**Version:** 1.0
**Status:** Infrastructure Specification
**Project:** NCA Batch 4 Private CTF Platform
**Purpose:** Define how CTF challenges are packaged, deployed, isolated, accessed, reset, monitored, and eventually migrated from local development to VPS production.

---

# 1. Purpose

The NCA Batch 4 Private CTF Platform must support multiple challenge types without requiring a separate server architecture for each challenge.

The infrastructure must support:

* Web challenges
* Pwn challenges
* Crypto challenges
* General challenges
* Downloadable challenges
* Containerized challenge services
* Per-challenge isolation
* Challenge health checks
* Challenge resets
* Resource limits
* Internal/private networking
* Administrative challenge management
* Local development
* Future VPS deployment

The same challenge should ideally work:

```text
Developer Laptop
        ↓
Local Docker
        ↓
Testing
        ↓
VPS Docker
        ↓
Production CTF
```

without requiring major application changes.

---

# 2. Important Infrastructure Principle

The CTF platform and challenge infrastructure must be treated as separate systems.

```text
                NCA CTF PLATFORM
                     │
          ┌──────────┴──────────┐
          │                     │
          ▼                     ▼
      Web/API                Database
          │
          │
          ▼
 Challenge Infrastructure Manager
          │
          ▼
        Docker
          │
    ┌─────┼──────────────┐
    ▼     ▼              ▼
  Web    Pwn         Other Services
```

The main CTF application should never become the vulnerable challenge itself.

---

# 3. Local-First Development Strategy

Since a production VPS may not be available initially, development must be local-first.

Development environment:

```text
Developer PC
│
├── CTF Frontend
├── CTF Backend
├── MySQL/MariaDB
└── Docker
     ├── Challenge 1
     ├── Challenge 2
     ├── Challenge 3
     └── Challenge N
```

The platform should be completely testable on one machine.

---

# 4. Future Production Architecture

When a VPS becomes available:

```text
Internet
   │
   ▼
Reverse Proxy
   │
   ├───────────────┐
   │               │
   ▼               ▼
CTF Platform     Challenge Network
   │               │
   ▼          ┌────┼─────┐
Backend       ▼    ▼     ▼
   │         Web  Pwn   Web
   ▼

```

The architecture must not depend on a specific VPS provider.


# 7. Standard Challenge Package

Every challenge should follow a standard directory structure.

Example:

```text
challenges/
└── web/
    └── jwt-misconfiguration/
        ├── challenge.yaml
        ├── README.md
        ├── Dockerfile
        ├── docker-compose.yml
        ├── src/
        ├── files/
        ├── scripts/
        └── tests/
```

Not every challenge requires every file.

---

# 8. Challenge Metadata File

Every deployable challenge must contain:

```text
challenge.yaml
```

Example:

```yaml
id: jwt-misconfiguration
name: JWT Misconfiguration
category: web
difficulty: medium
points: 200

deployment:
  type: http
  internal_port: 8080

healthcheck:
  path: /
  interval: 30
  timeout: 5

resources:
  cpu: "0.5"
  memory: "256M"
```

The exact schema may evolve.

The purpose is to make challenges portable.

---

# 9. Challenge Metadata Requirements

At minimum:

```text
id
name
category
difficulty
points
deployment.type
```

For network challenges:

```text
internal_port
```

Optional:

```text
healthcheck
resources
environment
startup_command
```

Secrets must never be committed into this file.

---

# 10. Dockerfile Standard

Example Web challenge:

```dockerfile
FROM php:8.3-apache

COPY src/ /var/www/html/

EXPOSE 80
```

The Dockerfile must create a self-contained challenge environment.

Do not depend on the host filesystem.

---

# 11. Container Principle

Each challenge should ideally have its own container or isolated service group.

Example:

```text
challenge-web-001
challenge-web-002
challenge-pwn-001
challenge-web-003
```

A vulnerability in one challenge must not automatically provide access to:

```text
CTF database
CTF backend
other challenge containers
host system
Docker socket
```

---

# 12. Container Isolation

Challenge containers must follow least privilege.

Avoid:

```text
--privileged
```

unless there is a documented challenge-specific requirement.

Do not mount:

```text
/var/run/docker.sock
```

inside normal challenge containers.

Do not mount sensitive host directories.

---

# 13. Network Isolation

Create separate Docker networks.

Conceptually:

```text
ctf_public
ctf_internal
challenge_network
```

Participant-accessible challenge containers should only expose the ports they actually need.

The challenge should not be able to freely access:

```text
MySQL
Redis
CTF backend
Admin interface
other challenge services
```

unless explicitly required.

---

# 14. Main Application Network

Example:

```text
ctf_frontend
      │
      ▼
ctf_backend
      │
      ▼
ctf_database
```

The database should not be publicly exposed.

Bad:

```text
Internet → MySQL:3306
```

Correct:

```text
Backend → Internal Docker Network → MySQL
```

---

# 15. Challenge Network

A challenge network may look like:

```text
challenge-network-001
       │
       ├── web
       └── database
```

If a challenge requires a database, the database should exist only inside that challenge's environment.

Example:

```text
Web Challenge
    │
    └── MySQL Challenge DB
```

Do not reuse the main CTF database for vulnerable applications.

---

# 16. Challenge Port Exposure

Never expose unnecessary ports.

Example:

```text
Container:
8080

Host:
random/high port
```

The infrastructure manager determines the externally reachable port.

Participants should receive:

```text
http://challenge-host:PORT
```

or preferably:

```text
https://jwt-misconfiguration.ctf.example
```

in production.

---

# 17. Dynamic Port Allocation

The system should support dynamic port allocation.

Example:

```text
Challenge A → 18001
Challenge B → 18002
Challenge C → 18003
```

The backend records the mapping in:

```text
docker_instances
```

Do not hardcode every challenge to port 80 or 443.

---

# 18. Future Subdomain Architecture

For a VPS deployment, prefer subdomains where practical.

Example:

```text
ctf.example.com
```

Main platform.

Challenges:

```text
jwt.ctf.example.com
upload.ctf.example.com
ssrf.ctf.example.com
```

Pwn:

```text
pwn01.ctf.example.com
```

or:

```text
nc pwn01.ctf.example.com 4001
```

A reverse proxy can route HTTP challenges.

---

# 19. Reverse Proxy

Recommended production architecture:

```text
Internet
   │
   ▼
Nginx / Caddy / Traefik
   │
   ├── ctf.example.com
   │       ↓
   │    CTF Frontend
   │
   ├── api.ctf.example.com
   │       ↓
   │    CTF Backend
   │
   └── *.ctf.example.com
           ↓
       Challenge Containers
```

The exact reverse proxy can be selected during implementation.

# 20. HTTPS

Production must use HTTPS.

Required for:

```text
CTF Platform
API
Challenge HTTP services
Admin interface
```

Challenge-specific HTTP behavior may intentionally use HTTP internally when required by the challenge.

Externally, TLS termination should normally happen at the reverse proxy.

```text
  ▼

  ▼

  │
  ▼
```

```text

    ↓
```

# 23. Challenge Health Checks

Every network challenge should ideally define a health check.

Web:

```text
GET /
```

Pwn:

```text
TCP connection test
```

Example:

```text
healthcheck:
  type: http
  path: /
  interval: 30
  timeout: 5
```

A challenge should only be considered operational after a successful health check.

---

# 24. Resource Limits

Every challenge container should have resource limits.

At minimum consider:

```text
CPU
Memory
Process count
Network
Disk
```

Example:

```text
CPU:
0.5 core

Memory:
256 MB
```

Values depend on the challenge.

Resource limits protect the host from intentionally or accidentally unstable challenges.

---

# 25. Challenge DoS Protection

Because vulnerable applications are intentionally exposed, a participant may accidentally or intentionally crash a challenge.

The platform should support:

```text
Health monitoring
Container restart
Rate limiting where appropriate
Resource limits
Instance reset
Admin restart
```

Do not assume challenge applications will always remain healthy.

---

# 26. Container Restart Policy

For suitable challenges:

```text
restart: unless-stopped
```

or equivalent infrastructure policy.

However, challenge-specific behavior may require:

```text
restart: on-failure
```

The infrastructure manager should decide based on challenge configuration.

---

# 27. Challenge Reset

Admin should be able to reset a challenge.

Example:

```text
STOP
 ↓
REMOVE
 ↓
RECREATE
 ↓
START
 ↓
HEALTH CHECK
```

Resetting must not delete:

```text
Submissions
Solves
Scores
Audit Logs
```

Only the challenge runtime is reset.

---

# 28. Stateful vs Stateless Challenges

Challenges should be classified.

## Stateless

Every participant interacts with the same logical challenge state.

Example:

```text
SQL injection challenge
```

## Stateful

Challenge contains mutable data.

Example:

```text
User account manipulation
File upload environment
Database modification
```

Stateful challenges may require per-team instances.

---

# 29. Per-Team Instances

Future architecture may support:

```text
Team A
   ↓
challenge-instance-teamA

Team B
   ↓
challenge-instance-teamB

Team C
   ↓
challenge-instance-teamC
```

This provides stronger isolation.

However, it requires more resources.

This feature should be considered optional for V1.


# 31. Challenge Flag Architecture

The challenge application should not depend on the main CTF database for flag validation.

Two systems exist:

```text
Challenge Environment
        │
        │ participant obtains flag
        ▼
CTF Backend
        │
        ▼
Flag Validation
```

The challenge may contain a flag or flag-generation mechanism.

The CTF backend remains authoritative for scoring.

---

# 32. Static Flags

```text

```

Static flags are appropriate for:

```text

Forensics
OSINT

```


Dynamic flags are useful for:


# 39. Challenge Build Process

When an admin publishes a Docker challenge:

```text
1. Validate metadata
2. Validate Dockerfile
3. Build image
4. Run container
5. Perform health check
6. Verify exposed service
7. Register instance
8. Mark challenge available
```

If any step fails:

```text
Deployment FAILED
```

The challenge should remain unpublished/unavailable.

---

# 40. Challenge Image Naming

Use predictable names.

Example:

```text
nca-ctf/web/jwt-misconfiguration:latest
```

Better production practice:

```text
nca-ctf/web/jwt-misconfiguration:v1
```

Challenge versions should be immutable where practical.

---

# 41. Challenge Versioning

A challenge may have:

```text
v1
v2
v3
```

If the vulnerability or application changes significantly, create a new challenge version.

Historical solves must remain associated with the correct challenge version where required.

---

# 42. Challenge Build Security

Do not build untrusted challenge code directly on the production host without controls.

For V1:

```text
Trusted challenge authors
```

may prepare images.

Future architecture may use:

```text
Dedicated build worker
```

for stronger isolation.

---

# 43. Docker Socket Security

Never expose Docker socket to:

```text
CTF backend
```

unless absolutely necessary.

If the backend needs Docker control, prefer a dedicated infrastructure service.

Architecture:

```text
CTF Backend
     │
     ▼
Infrastructure Manager
     │
     ▼
Docker
```

The infrastructure manager is the only component with Docker privileges.

---

# 44. Infrastructure Manager

Responsibilities:

```text
Build challenge
Start container
Stop container
Restart container
Remove container
Check health
Collect status
Allocate ports
Register instance
```

It must not contain participant-facing functionality.

---

# 45. Docker API Security

The infrastructure manager must validate every requested operation.

Never accept arbitrary Docker commands from the frontend.

Bad:

```text
POST /docker
{
  "command": "docker run ..."
}
```

Correct:

```text
POST /internal/challenges/:id/start
```

The server determines the actual Docker operation.

---

# 46. Challenge Environment Variables

Environment variables may be used for challenge configuration.

Example:

```text
DATABASE_HOST
DATABASE_NAME
APP_ENV
FLAG
```

However:

* Secrets must not be exposed through the CTF API.
* Admin logs must not accidentally print secrets.
* Environment variables must be scoped to the challenge.
* Challenge containers must not inherit unnecessary host secrets.

---

# 47. Challenge Secrets

Do not store production secrets inside challenge images.

For example, never place:

```text
CTF_DATABASE_PASSWORD
ADMIN_PASSWORD
APP_SECRET
DOCKER_TOKEN
```

inside a challenge container.

A vulnerable challenge should only receive the secrets intentionally designed for that challenge.

---

# 48. Container Filesystem

Where possible:

```text
read-only filesystem
```

can be used with writable temporary directories when compatible.

For intentionally vulnerable challenges, this may not always be practical.

Security must be balanced with challenge requirements.

---

# 49. Host Protection

Challenge containers must not be able to:

```text
Access host filesystem
Access Docker socket
Modify host networking
Load kernel modules
Run privileged operations
Access unrelated containers
Access host secrets
```

unless the challenge explicitly requires a controlled exception.

---

# 50. Database Separation

Never allow a vulnerable Web challenge to use:

```text
NCA CTF database
```

Instead:

```text
Challenge
   ↓
Challenge-specific DB
```

Example:

```text
sql-vault
   │
   ▼
sql-vault-db
```

This is critical.

A SQL injection challenge must not accidentally provide access to:

```text
users
teams
submissions
flags
```

from the main CTF database.

---

# 51. Challenge-to-Platform Boundary

The intended relationship is:

```text
Challenge
   │
   │
   │     NO DIRECT ACCESS
   │
   X ───────────────► CTF Database
   X ───────────────► CTF Backend
   X ───────────────► Admin Panel
```

Participants interact with the challenge and separately submit the resulting flag to the CTF platform.

# 53. Challenge Logs

Admins may view challenge logs.

Example:

```text
GET /api/v1/admin/containers/:id/logs
```

Logs must be protected.

Do not expose challenge logs to participants by default.

Logs may contain:

```text
Passwords
Tokens
Flags
User input
```

Therefore they must be treated as sensitive.

---

# 54. Automatic Recovery

The infrastructure manager may restart failed containers.

Example:

```text
Container unhealthy
        ↓
Health check failure
        ↓
Restart
        ↓
Health check
        ↓
Healthy
```

If repeated failures occur:

```text
Healthy
  ↓
Failure
  ↓
Restart
  ↓
Failure
  ↓
Restart
  ↓
Failure
  ↓
Mark FAILED
```

Avoid infinite restart loops.

---

# 55. Challenge Availability

The frontend should show:

```text
Available
Starting
Unavailable
Maintenance
```

based on backend state.

Do not let the frontend assume:

```text
container == running
```

means the challenge is actually usable.

Health status matters.
